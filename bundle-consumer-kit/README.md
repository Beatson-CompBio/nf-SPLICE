# SPLICE bundle consumer kit

Agent and skill files for developers who **build on** SPLICE workflow
bundles: ingestion services and the SPLICE database, web interfaces, data
explorers, job launchers and anything else that reads `bundle.json`,
`inputs.schema.json`, `outputs.schema.json`, `components.json`,
`execution-profiles.json` or a job's `analysis_output.json`.

You do **not** need nf-splice, Python or Nextflow to use this kit. nf-splice
is the tool workflow developers use to *produce* bundles; this kit is for the
people who *consume* them. Drop the files into your own repository and your
coding agent (Claude Code, Codex, Cursor, GitHub Copilot or any agent that
reads `AGENTS.md` or skill files) learns the structure, the meaning of every
key and value, and how to validate against the versioned schemas.

## What is in the kit

| Path | What it is |
| --- | --- |
| [`AGENTS.md`](AGENTS.md) | Drop-in instructions for your repository's coding agent. |
| [`skills/`](skills/) | Five skills, one per kind of work (below). |
| [`schemas/`](schemas/) | The formal JSON Schema definitions of the five contracts, by revision, each with an example. |
| [`examples/bundle/`](examples/bundle/) | A complete, validated bundle of a small RNA-seq workflow with two alternative aligners and an optional quantification step. |
| [`examples/analysis_output.json`](examples/analysis_output.json) | The `analysis_output.json` of one completed job of that workflow, which took the STAR route. |

The schemas and examples are generated by nf-splice and checked in its test
suite, so they always match what nf-splice publishes.

## Which skills you need

| You are building | Use these skills |
| --- | --- |
| Anything that reads a bundle | [`splice-bundle-contracts`](skills/splice-bundle-contracts/SKILL.md), always |
| Ingestion into the SPLICE database, or any store | [`splice-bundle-ingestion`](skills/splice-bundle-ingestion/SKILL.md), [`splice-analysis-output`](skills/splice-analysis-output/SKILL.md) |
| A web interface: workflow catalogue, launch forms, results pages | [`splice-web-ui`](skills/splice-web-ui/SKILL.md), [`splice-analysis-output`](skills/splice-analysis-output/SKILL.md) |
| A data explorer or anything reading job results | [`splice-analysis-output`](skills/splice-analysis-output/SKILL.md) |
| The service that launches jobs on compute | [`splice-job-launch`](skills/splice-job-launch/SKILL.md) |

`splice-bundle-contracts` is the foundation every other skill builds on:
structure, versions, identity and validation. Install it with whichever role
skills fit your work. If your service reads the database rather than the
bundle files, the role skills still apply: they describe what each stored
field means and how it should be used.

## Install into your coding agent

Copy the kit into your repository, for example as `docs/splice/`, or keep it
as a Git submodule pinned to an nf-SPLICE release so updates are deliberate.

**Agents that read `AGENTS.md`** (Codex, Cursor, GitHub Copilot, OpenCode and
others): copy or merge [`AGENTS.md`](AGENTS.md) into your repository's
`AGENTS.md`, and keep the `skills/`, `schemas/` and `examples/` folders at
the paths it names.

**Claude Code:** copy each folder under `skills/` into `.claude/skills/` in
your repository; Claude Code discovers them by their `SKILL.md`. Add the
contents of `AGENTS.md` to your `CLAUDE.md`, or reference it from there.

**Other agents with skill folders:** each skill is a folder with a
`SKILL.md` that starts with `name` and `description`; copy the folders to
where your agent discovers skills.

Edit the copy's paths if you move `schemas/` or `examples/`. The skills refer
to them as `schemas/<family>/v<revision>/schema.json` and `examples/...`
relative to the kit's root.

## Keeping up to date

Each kit belongs to one nf-SPLICE release and covers the contract revisions
that release writes. This kit covers revision **0.3.0** of all five
families. When a new nf-SPLICE release changes a contract revision, its
kit adds the new `schemas/<family>/v<revision>/` folder and updates the
skills; earlier revisions stay, so your code can support more than one.
Compare `schemas/` between kit versions to see what changed.

## The concepts in one paragraph

A **bundle** is a static folder (`splice/`) that describes one released
version of one workflow: who made it (`bundle.json`), what parameters it
takes and who may set them (`inputs.schema.json`), every kind of output it
can publish (`outputs.schema.json`), the software and containers it runs
(`components.json`) and the reviewed ways to run it
(`execution-profiles.json`). A **job** is one execution of that workflow
version. A completed job produces one `analysis_output.json`: an inventory
of the outputs that job actually published, each owned by the job, a
**sample** or a **run** (a platform file-level unit of a sample), and each
pointing back to its kind in the bundle's output catalogue.
